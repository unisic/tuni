# Packaging

Everything installs through the top-level `Makefile`, so each format below only
has to say where its prefix is. `make install PREFIX=/usr DESTDIR=…` puts down
the binary, the desktop entry, the AppStream metadata, and the two icons.
Themes are baked into the binary at build time, so there is no data directory
to carry.

## What the build needs

Two things beyond the usual GTK development headers:

- **Zig 0.17.0.** `libghostty-vt` is Zig source compiled during the build,
  and Ghostty 1.4 declares 0.17.0 its minimum; Fedora 44 ships 0.16. Every
  build path here fetches the official tarball by URL and checksum rather than
  trusting `zig` on PATH, and `make zig` does the same thing for a working
  copy, into `~/.local`.
- **The Ghostty 1.4.0 release.** `libghostty-rs` pins a Ghostty commit without
  the fix for GHSA-w9q4-5jvv-mcv4, so `make build` fetches the release tarball
  by URL and checksum, unpacks it in the target directory, and hands it to the
  build as `GHOSTTY_SOURCE_DIR`. A `GHOSTTY_SOURCE_DIR` already set is used as
  it is.
- **Network**, unless it is given a way not to. The Makefile fetches the
  Ghostty release, and cargo fetches the registry.

Both have an offline path, which is what a distribution build would use:

| Variable | Effect |
| --- | --- |
| `GHOSTTY_SOURCE_DIR` | The Ghostty release unpacked, used instead of fetching one. It has to be writable: Zig 0.17 unpacks the packages it fetches into `zig-pkg/` beside `build.zig` |
| `GHOSTTY_ZIG_SYSTEM_DIR` | A directory of Zig package dependencies, so `zig build` runs with `--system` |
| `CARGO_HOME` | A populated registry, alongside `cargo build --offline` |

## Flatpak — `dev.unisic.Tuni.yml`

```sh
flatpak-builder --user --install --force-clean \
    --install-deps-from=flathub build packaging/dev.unisic.Tuni.yml
```

The manifest builds with `--share=network`, which is what makes it a local
manifest rather than a Flathub submission. Flathub builds offline, so a
submission needs, on top of this file: cargo sources generated by
`flatpak-cargo-generator.py` from `Cargo.lock`, and Ghostty's Zig
dependencies pre-fetched for `GHOSTTY_ZIG_SYSTEM_DIR`. The Zig toolchain and
the Ghostty source are already `archive` sources pinned by URL and checksum
here.

`--filesystem=host` is deliberate and not reducible: a terminal workspace whose
file tree, Git panel, and shells could only see their own sandbox would be a
terminal that cannot see the code being worked on.

## RPM — `tuni.spec`

```sh
make dist
rpmbuild -ba --define "_sourcedir $PWD" packaging/tuni.spec
```

For COPR with network enabled, or a local build. Koji builds offline, so a
Fedora package proper would want the same offline sources the Flathub build
does, plus `cargo vendor`.

## deb — `debian/`

```sh
apt install rustup && rustup default stable   # Ubuntu's rustc is too old
make zig ZIG_PREFIX=/usr/local                # Ubuntu's zig is too new
cp -r packaging/debian debian
dpkg-buildpackage -b -us -uc
```

Ubuntu 26.04 or later, for libadwaita 1.6; earlier releases are below it and
the Flatpak is what covers them. Neither toolchain comes from the distribution:
26.04 packages rustc 1.93 and rusqlite 0.40 wants 1.95, so `rustup` provides
the compiler the same way the Flatpak's SDK extension does. `debian/rules` only
tells debhelper the prefix; the top-level `Makefile` installs, as everywhere
else here.

It lives under `packaging/` with the rest and gets copied to the root for the
build, rather than sitting at the top of the tree the whole time.

## Arch — `arch/PKGBUILD`

```sh
make dist && mv tuni-1.7.0.tar.gz packaging/arch/
cd packaging/arch && makepkg -si
```

The pinned Zig comes down as a second `source` entry, by URL and checksum,
rather than whatever Arch's `zig` has moved to by the time the package is
built. `build()` still wants the network for cargo and the Ghostty source.

## Which CPU a package is built for

`zig build` compiles for the machine it runs on unless told otherwise. That is
right for a build that stays where it was made and wrong for a package: 1.1.1
was compiled on a GitHub runner with AVX-512 and died with SIGILL, in `memset`,
before the window appeared, on every machine without it.

`libghostty-vt-sys` now passes `-Dcpu` itself, from `LIBGHOSTTY_VT_SYS_CPU`,
and defaults to `baseline`. `make build` sets that variable from `ZIG_CPU`, so
every package format here, all of which go through `make build`, has one place
where this is decided. `make build ZIG_CPU=native` is the other way, for a
build that is not going anywhere.

The Rust half needs nothing: rustc already targets the baseline unless asked
for more. Vector code that dispatches on CPUID at runtime, which is most of
what makes a terminal fast, is unaffected and still used.

`scripts/check-baseline.sh` reads the instructions back out of a built binary
and refuses one that went out compiled for its build machine. CI runs it, and
so does every package job, on the binary it just installed.

## COPR (`../.packit.yaml`)

Packit builds each GitHub release from `tuni.spec` into the COPR project
`debondor/Tuni`. The project is set up once, by hand: internet access during
builds turned on, since the spec fetches cargo crates, the Ghostty source and
Zig; the Fedora chroots ticked, which is the list Packit builds for; and
`github.com/unisic/tuni` under "Packit allowed forge projects". The Packit
GitHub App has to be enabled for this repository too.

## AUR (`aur/`)

`aur/tuni` builds the tag archive from source, the way `arch/PKGBUILD` builds a
local one, and `aur/tuni-bin` repacks the release's Arch package. Both leave
`/usr/share/tuni/install-channel` behind, which is how the update dialog knows
to leave updating to the helper.

```sh
packaging/aur/sync.sh --version 1.7.0 --check   # retarget, .SRCINFO, build both
```

`sync.sh` takes the checksums from the published release, so it runs after
one. `--push` publishes, which `.github/workflows/aur.yml` does after a release
once the repository variable `AUR` is `on`, with the `AUR_SSH_KEY` secret: a
private key registered on the AUR account, base64'd onto one line. Neither is
set yet, so releases skip the AUR.

```sh
base64 -w0 < ~/.ssh/aur | gh secret set AUR_SSH_KEY --repo unisic/tuni
gh variable set AUR --body on --repo unisic/tuni
```

## Releases

`.github/workflows/release.yml` builds all three on a `v*` tag and attaches
them to the GitHub release, whose notes are that version's section of
`CHANGELOG.md`. Packit sees the same release and builds it into COPR, and with
`AUR` on the workflow pushes both AUR recipes too. Every job installs what it
built before uploading it. Six files carry the version: `Cargo.toml`, the spec,
the PKGBUILD, the Debian changelog, the AppStream metadata and `CHANGELOG.md`.
The first job in the workflow refuses to release if they disagree with each
other or with the tag.

## Not here

**AppImage.** For a GTK 4 program it means bundling GTK, libadwaita and
GtkSourceView, and then either building on something old enough to run
everywhere and too old to have libadwaita 1.6, or building on something current
and shipping a glibc floor no older distribution meets. Flatpak solves that
problem properly and is already here. A terminal workspace is also the last
program that wants to be relocatable and sandboxed away from the system it is
working on.
